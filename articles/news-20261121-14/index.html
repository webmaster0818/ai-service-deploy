AI・システム・セキュリティのニュースまとめ（2026年11月21日 14時）

公開 2026-11-21　AIサービス比較ナビ 編集部

2026年11月21日8時の回以降に確認したニュースのうち、公式発表を確認できた6件をまとめました（セキュリティ 3件、AI 1件、システム・開発基盤 2件）。 F5のBIG-IPの緊急修正、N-ableのメールフィルタリング基盤への不正アクセス、CiscoのJava4Shellの影響調査、AIエージェントがゼロデイを見つけて悪用した事例などを取り上げます。

当サイトでは、各社・各機関の公式発表を開いて内容を照合したうえで掲載しています。数字や日付は各項目末尾の出典番号から確認できます。今回の時間帯は米国の週末にあたり新しい発表が少なかったため、11月18〜20日に公表され、これまでの回に載せられなかった発表も含めています。時刻は日本時間で記載しています。

セキュリティ

1. F5、BIG-IPに深刻度「Critical」の脆弱性6件　回避策はなく緊急のホットフィックスで対応

F5は2026年11月18日（米国時間）、定例外のセキュリティ通知を公開しました。通知にはNGINXの脆弱性（当サイトで既報）のほか、BIG-IPとBIG-IQの脆弱性が含まれています [1]。このうちBIG-IP APMの脆弱性（CVE-2026-123637）と、iRuleの特定のコマンドを使う設定で影響を受ける5件（CVE-2026-120285、CVE-2026-120292、CVE-2026-116953、CVE-2026-121805、CVE-2026-120722）は、深刻度がいずれもCritical（CVSS v3.1で9.8）です [1][2][3][4][5][6][7]。 F5によると、認証されていない遠隔の攻撃者が細工したリクエストを送ると、トラフィックを処理するTMMが停止してサービス妨害（DoS）が起き、遠隔コード実行に至るおそれがあります。影響はデータプレーンに限られ、管理側（コントロールプレーン）は影響を受けないとしています。CVE-2026-123637とiRuleの5件の緩和策は「なし」とされ、修正は通常のリリースではなくエンジニアリングホットフィックスとして提供されています [2][3][4][5][6][7]。 F5は11月21日、ホットフィックスの適用で選ぶべきビルドの案内を更新しました。対象はBIG-IP 21.1.x、17.5.x、17.1.xで、現在のバージョンや適用済みのホットフィックスに応じて入れるビルドが異なります [8]。あわせて公開されたBIG-IP APMのSAMLの脆弱性（CVE-2026-126822、High）は、SAMLのサービスプロバイダー機能が不要ならアクセスポリシーからSAML認証エージェントを外すことなどを緩和策として挙げています [9]。

企業・担当者が確認すること： BIG-IPを使っている企業は、F5の通知の一覧で自社が使うモジュールとiRuleのコマンドが該当するかを確認し、案内に沿ってホットフィックスを適用してください [1][8]。F5はエンジニアリングホットフィックスについて、通常のリリースほどの品質検証を経ていないとしています [2]。当サイトでは、適用前に設定のバックアップを取り、検証用の機器があれば先に試すことをおすすめします。

2. N-able、メールフィルタリング「Mail Assure」「SpamExperts」に不正アクセス　管理画面とAPIの停止が続く

IT管理サービスのN-ableは、メールフィルタリングサービス「Mail Assure」と「SpamExperts Hosted Cloud」で起きている障害について、障害情報ページで経過を公表しています。障害は11月17日12時に始まり、11月18日12時5分の更新で、当初の説明（設定とサービスの依存関係が原因）を改め、原因はセキュリティインシデントだったと説明しました [10]。 同社は、ホステッドクラウド環境のサーバー1台への不正アクセスを把握しているとしたうえで、現時点で顧客データや利用者のメールボックスへのアクセスを示す証拠はないとしています。米州・アジア太平洋・欧州の全リージョンで、管理画面、API、隔離メールの閲覧、ログの確認が止まっています。メールの配送とフィルタリングは動き続けているとしています [10]。 11月21日2時45分の更新では、修復と安全性の検証が大きく進み、復旧の準備に入ったとしています。管理画面とAPIは復旧作業が始まるまで停止したままです [10]。対応が必要かどうかについては、11月19日5時18分の更新で、パートナーにメールで個別に連絡したとしています [10]。

企業・担当者が確認すること： 両サービスを使っている企業や、そのサービスを提供している販売・保守事業者は、N-ableからのメールで対応の要否を確認してください [10]。当サイトでは、管理画面が止まっている間に隔離されたメールを確認できないことから、取引先からの重要なメールが届いていないと連絡を受けた場合の確認手順を、社内で決めておくことをおすすめします。

3. Cisco、OpenJDKの脆弱性「Java4Shell」の影響製品を公表　修正版の提供時期は未定のものが多く（続報）

Ciscoは11月21日5時37分、OpenJDKの脆弱性「Java4Shell」（CVE-2026-114938）が自社製品に与える影響についてのアドバイザリを更新しました（バージョン1.3、調査継続中）。影響を受ける製品として、Secure Network Analytics、Secure Workload、Finesse、Unified Contact Center Enterprise、Unified Customer Voice Portal、HyperFlex HX Data Platform、Intersight Virtual Appliance、Smart Software Manager On-Premなどを挙げています [11]。 多くの製品で修正版のリリース番号や提供時期は「TBD（未定）」となっており、Secure Network Analyticsは7.6.1、7.6.0、7.5.3向けのパッチを予定しているとしています。Cisco製品については回避策はないとしています。ISE、IOS XE、ASA、Firewall Threat Defense、Catalyst Centerなどの優先製品は影響を受けないとしています。影響を受けるのはAVX-512 VBMIに対応したx86-64のCPUを使うシステムで、ARMなどのアーキテクチャは影響を受けないとしています [11]。

企業・担当者が確認すること： 一覧に挙がっているCisco製品を使っている企業は、アドバイザリの更新を追い、修正版が出たら適用してください [11]。当サイトでは、Javaを同梱する他社の製品についても、各ベンダーの影響調査の結果を確かめることをおすすめします。

4. Amazon、AIエージェントが自力でゼロデイを見つけて悪用した事例を報告

Amazonの脅威インテリジェンスチームは2026年11月20日（米国時間）、中国系とみられる攻撃者が、オープンソースのAIペネトレーションテスト基盤「Cairn」を使って攻撃していた事例を公表しました。攻撃者がCairnを認証なしで外部公開していたため、指示内容やAIの出力を含む操作の記録を確認できたとしています。9月8日から約48時間、中国本土以外の東アジアの大学を狙い、AIエージェントに「シェルアクセスを得よ」という目標だけを与えていました [12]。 オープンソースの医用画像AIアプリケーションに対しては、エージェントがAPIを調べ始めてから約11分で、ファイル名のパラメータのパストラバーサルの脆弱性を見つけ、サーバーに任意のファイルを書き込めるようになりました。その後、別のセッションでroot権限のリバースシェルを得ています。この脆弱性は当時、修正も公表もされていないゼロデイだったと高い確度で評価しています。一方、Redisサーバーへの約16時間・148回の試行や、3万通り以上の認証情報を試したGPUサーバーへの攻撃は失敗したとしています [12]。 Amazonの通知を受けて、開発元はアドバイザリと修正を公開しました [12]。脆弱性があったのは医用画像向けの「MONAI Label」で、11月18日公開のアドバイザリでは深刻度をCriticalとしています [13]。

企業・担当者が確認すること： Amazonは、AIエージェントによる攻撃は人が警報を一つずつ確認するより速く進むため、確度の高い検知から自動で対応する仕組みを優先するよう勧めています [12]。当サイトでは、研究用途などでインターネットに公開しているAIアプリケーションやデータベースに、認証がかかっているかを点検することをおすすめします。

5. AWS Network Firewall、全VPCのインターネットゲートウェイに一括で適用できる機能をプレビュー公開

AWSは2026年11月20日、AWS Network Firewallの「automated Internet firewall」をパブリックプレビューとして公開しました。中央で定めたファイアウォールのルールを、対象とするVPCのインターネットゲートウェイを通る通信のすべてに適用する機能で、NAT機能も備えています。ルーティングや構成を変えずに導入でき、特定のVPC、アカウント全体、組織単位などで有効にできます [14]。 これまでは、VPCごとに専用のサブネットにファイアウォールを置き、経路を更新する必要がありました。新しく作るVPCやサブネットに組織のセキュリティポリシーを自動で広げる設定もできます。AWSのマネージドルールを使った既定のポリシーが用意されています。GovCloudと中国を除く全リージョンで利用できます [14]。

企業・担当者が確認すること： 複数のVPCでインターネットとの通信を管理している企業は、検証用のアカウントで、既存のルールや経路との関係を確かめてください [14]。当サイトでは、プレビュー段階の機能は料金と制約を料金ページと技術文書で確認してから本番への適用を判断することをおすすめします。

6. GitHub、セキュリティアドバイザリの作業権限をカスタムロールで付与可能に

GitHubは2026年11月20日、リポジトリのセキュリティアドバイザリと非公開の脆弱性報告を扱う権限を、カスタムリポジトリロールで付与できる機能を一般提供しました。これまでは、リポジトリ管理者や組織全体のセキュリティマネージャーの権限を与える必要がありました [15]。 追加された権限は、アドバイザリの閲覧、作成・編集・管理、非公開の脆弱性報告の受け付けとアドバイザリのクローズ・再オープン、アドバイザリの公開とCVEの要求の4つです。一時的な非公開フォークからの変更のマージには、引き続きリポジトリ管理者かセキュリティマネージャーの権限が必要です。カスタムリポジトリロールに対応したプラン（GitHub Enterprise Cloudなど）で使えます [15]。

企業・担当者が確認すること： OSSや社内ライブラリを公開している企業は、脆弱性報告に対応する担当者に、必要なリポジトリだけの権限を付けられるか確認してください [15]。当サイトでは、管理者権限を広く配っている場合は、この機能を使って権限を絞ることをおすすめします。
